Model comparison

The project deliberately used several models in distinct roles: one to plan, a different one to critique the plan, and two more to implement the same specification independently. This page reports what happened.

Implementations A and B must come from different models. If one model built both, there is nothing to compare and the exercise collapses. This is recorded as a condition in the project's definition of done.

2. The critique round

The plan was handed to a second model with explicit instructions to attack it and to sort its findings into errors, omissions and preferences. It returned 14 findings. All 14 were accepted; two were implemented differently from the fix that was proposed.

The critic verified the physics derivations and all three worked examples by independent calculation, and they held — no equation changed as a result of the critique. What it did find was one error that would have actively misled an implementer, one that could have caused a wrong guard in the tool's headline interaction, and a systematic traceability failure between two documents.

The findings that mattered most

IDFindingOutcome
C-03 The plan said the worked example had "three complete risers, the third truncated" — which is self-contradictory. It has two complete risers plus a truncated third. Accepted. The serious part was downstream: an acceptance criterion demanded "3 complete risers", so a correct implementation would have failed the check and sent someone hunting a bug that did not exist.
C-04 The plan's wording implied that an absorption factor below 1 is infeasible. Accepted, and the risk was larger than reported. Checking all four presets showed A < 1 is reachable on every one. An implementer adding an A ≥ 1 guard would have broken the exact regime the tool exists to demonstrate.
C-01 Eight of ten cross-references between the plan and the decision log pointed at the wrong entry. Accepted. An artefact of writing the two documents in different orders and never reconciling them. Now verified programmatically.
C-05 The clamping functions returned inconsistent labels for which limit had been hit. Accepted, fixed differently. The proposed unification would have labelled a liquid-rate cap as a thermodynamic pinch. It is a user-interface limit, not physics, and telling a student otherwise teaches something false. The two concepts are now reported separately.
C-12 Add a demonstration preset just off A = 1, to exercise the numerical branch selection rather than only the special case. Accepted, value corrected. The suggested value sits exactly on the branch threshold and so takes the other code path — it would not have tested what it was meant to test.

Where the critic was wrong, and how that was caught

Two findings had correct conclusions supported by incorrect reasoning. One mislocated which operating limit produces a particular value; the other proposed a numerical value on the wrong side of a strict inequality. Both were found by recomputing the claim rather than reading it. The fixes were adopted and the reasoning corrected.

This is the most transferable lesson of the exercise: a critique is evidence, not a verdict. A second model is very good at finding things the author cannot see in their own work, and is also capable of being confidently wrong in the same breath. Checking it is part of the process, not a sign of distrust.

Your reading of the critique round. The record: 14 findings, all accepted, two fixed differently from what was proposed, and two where the critic's conclusion was right but its reasoning was wrong.

The sharpest question is whether the step paid for itself. One finding (C-03) would otherwise have shipped an acceptance criterion that a correct implementation fails — someone would have spent an afternoon hunting a bug that did not exist. Another (C-04) would likely have produced a guard that broke the tool's headline interaction. Against that: the critique also produced findings that were mostly bookkeeping.

Would you run this step again? And does "the critic was confidently wrong twice" change how you would use one?

3. Implementation A versus B

Both implementations were written against the same frozen module interface and graded by the same test suite, which runs against either one by pointing an environment variable at it.

What the grading actually showed

The physics converged exactly. Not "closely" — the two implementations return the same doubles across 4,837 operating points. The specification prescribed the log1p forms and the numerical branch thresholds down to the constant, and that was apparently enough to remove all freedom from the result. This is the strongest evidence in the project that writing the plan first was worth the effort.

Both avoided the trap the plan's own author fell into. The fractional-stage rule was the error in plan v1.0 — 2.375 against a correct 2.459432 — caught by the critique. Both implementations got it right, because by then the plan explained it. A defect found in planning was prevented twice over in implementation.

But implementation B's site does not run. Three of its twelve JavaScript modules fail to parse, each from a single-character typo:

FileCause
js/drag.js Unterminated string literal — e.key==='ArrowLeft is missing its closing quote
js/render-ntu.jsOne extra }
js/render-profile.jsOne extra }

Because drag.js never parses, no handle is wired: the demo renders no SVG and nothing can be dragged. All six pages still return HTTP 200, so a casual check would miss it entirely.

And the test suite was wrong. Implementation B's first run scored 44/61 — but sixteen of those seventeen failures had nothing to do with its physics. The suite was calling gFactor, xOutPinch, yOutRange, xOutRange, TOL_N, TOL_G and guardHit: all things implementation A happens to export, none of them in the contract the two models were given. The claim that both implementations pass "the same suite, unmodified" was not true as written — the suite encoded implementation A rather than the specification. Rewriting it to use only the published API took B from 44/61 to 60/61, and the single remaining failure is a field the specification genuinely omitted.

ⓘ
On fairness. That last failure is recorded as a specification gap at build time, not as a defect in implementation B. It was built against the contract as published, which did not contain the field. The specification has since been amended; implementation B has deliberately not been patched, so the artifact remains exactly what the model produced.

Round 2 — and what it changed

Implementation B was sent a targeted defect report naming the three syntax errors precisely, and returned 3,572 lines of changes plus a written report. Everything asked for was delivered: readable source, the three errors fixed, the height probe finally wired, and all six pages built out. The site now works — SVG renders, all three handles drag, all three respond to the keyboard.

And the physics is still bit-identical to implementation A across 4,837 operating points, now including the amended LoVratio field. Two independent implementations, a specification, and a round of substantial rewriting later, and they still return the same doubles.

One defect remains, and it is instructive: implementation B's state.js creates its initial derived state at module load but only attaches the probe data inside its update function, so the very first render throws before it finishes. It self-corrects the moment anything is dragged, which is exactly why it survives casual use — the page looks fine, and only the console knows.

⚠
The comparison is not symmetric, and should not be read as though it were. Implementation B received a detailed defect report and a second attempt. Implementation A received neither — it was verified in a browser as it was built, which is why its equivalent defects were caught before they were ever committed. Round 2 measures "can this model fix precisely-described faults", which is a real and useful capability, but it is a different question from round 1's "what does this model produce from a specification alone".

A note on the measurements themselves

Twice during this project the instrument was wrong rather than the thing being measured. The shared test suite silently encoded implementation A rather than the specification, and failed implementation B sixteen times for reasons unrelated to its physics. Later, a browser probe reported "drag is dead" when it had simply aimed at an element scrolled outside the viewport and pushed a control in a direction it was already clamped against.

In both cases the implementation was blamed first, and in both cases it was innocent. That is worth carrying out of this project: when an automated check disagrees with a piece of work, the check is a hypothesis too.

The outcome: implementation A was chosen

After viewing both running side by side, implementation A was chosen as the version to carry forward. The root URL now opens it; implementation B remains in the repository in full, and both are still browsable together at the comparison view.

It is worth being precise about what that decision was and was not. It was not a judgement that A is more correct: the two agree to the last digit across 4,837 operating points, and both pass the shared suite 65/65. It was a preference between two defensible interface designs — most visibly, B opens with a landing section and a call to action, while A puts the tool on screen immediately.

⚠
Two asymmetries the choice should be read against. B received a targeted defect report and a second attempt; A received neither, because it was verified in a browser as it was built. And A's supporting pages were written out in full while B's were left largely as placeholders, so A was further along as a document regardless of its interface. A like-for-like judgement on interface alone would have to discount both.

The visible design disagreement was the opening: B leads with a landing section and a call to action, A puts the tool on screen immediately. For a class demo where the audience already has the context, that is a real trade-off rather than an obvious win either way.

Also worth saying plainly: is there anything B did better that you gave up by choosing A? A comparison that finds nothing good in the option not taken is usually a comparison that was not really made.

Three lessons worth stating

  1. A precise specification removes variance. Where the plan was prescriptive, the two models produced identical output. Where it was silent — it never said "write readable source" — they diverged completely.
  2. Passing the tests is not the same as working. The physics module scored 60/61 while three sibling modules would not parse. The plan put its hard gate on the pure layer and got exactly what it asked for. That is a gap in the plan's verification strategy as much as in the implementation.
  3. Unreviewable code hides cheap mistakes. Three one-character typos, fatal, invisible in twelve single-line files.

The comparison in prose. The table above gives the numbers; the argument is yours. The most striking fact to build around is that the physics converged exactly while everything else diverged completely — same duty, same equations, same doubles, and two entirely different websites.

Worth addressing: which would you rather maintain six months from now? Did the detailed specification make them converge, or did it only constrain the part that was already easiest to specify? And is that a limit of this plan, or a limit of specifications in general — that you can pin down a formula far more tightly than you can pin down an interface?

4. What the process suggests about these models

Your conclusions. Four questions worth answering directly, each with evidence already on this page:

  • Did planning first help? The bit-identical physics says yes for anything the plan specified precisely. The completely divergent interfaces say it did nothing for anything it left open.
  • Was the critique worth its cost? It caught a real physics error and a real specification trap, and was also wrong twice.
  • Did the shared suite change the outcome or just measure it? It measured — and then turned out to be measuring the wrong thing until the second implementation exposed it.
  • Where did you supply judgement no model supplied? The overrides are listed in the documentation page. The one worth dwelling on is keeping a broken artifact unrepaired so that the comparison stayed honest — no model suggested that.

The full decision log, including every point where the project owner overrode a model's recommendation, is kept in docs/DECISIONS.md in the repository. Entries marked as owner overrides are the direct record of human steering.
