Documentation

How the explorer works, the physics behind every number on it, and how it was built and checked.

1Overview

This site puts a tray column and a packed column side by side doing the same dilute gas absorption job: the same solute, the same entering gas and liquid compositions, the same required outlet purity, and the same molar flow rates. Everything about the duty is identical. Only the hardware differs — and the point of the tool is to let you watch the two designs size themselves differently, live, as you change the duty.

The interaction is deliberately direct manipulation rather than sliders. There are three things you can grab:

  • the lower-left end of the operating line, yout, dragged vertically, which sets how clean the treated gas must be;
  • the upper-right end of the operating line, xout, dragged horizontally, which sets the liquid rate;
  • a height probe, dragged up and down the two columns, which reads the local gas composition in each.

Everything else on the page is a consequence of those three. The stage count, the tray count, the packed height, the transfer-unit area, the composition profiles and the comparison table all recompute on every pointer move.

On the diagram the column appears upside down, which is worth saying once. The lower-left end of the operating line, (xin, yout), is the top of the column: fresh liquid enters there and the treated gas leaves. The upper-right end, (xout, yin), is the bottom of the column: the feed gas enters and the rich liquid leaves. The diagram is ordered by composition, not by height.

2Framing: this is an AI project

This is an AI project for the Separation Processes course, and the process is as much the artefact as the website. The brief was not "build a tool" but "explore what these models can and cannot do, and document it honestly."

Concretely, that meant a deliberate pipeline: one model wrote a detailed implementation plan before any code existed; a different model critiqued that plan; the critique was adjudicated point by point; and then the revised plan was implemented independently by two different models against a shared, unmodifiable test suite. The model comparison page reports what came out of that.

Two design choices exist purely to make the exploration honest:

  • The physics lives in a pure module with no access to the page, and is checked by a test suite that both implementations must pass unmodified. Without a fixed bar, "which model did better" is an impression; with one, it is a measurement.
  • Every design decision is logged with a rationale and an attribution — owner, assignment, or model — in a running decision log, including the cases where the human overrode the model's recommendation. Those overrides are the most interesting entries, because they are the places where judgement was actually exercised rather than delegated.

3The process — models, tools, prompts

The models, and what each one did

Four distinct roles, deliberately kept separate so that no model was asked to check its own work:

CriticMuse AI 14 findings against the plan, sorted into errors, omissions and preferences
Implementer AClaude Opus 5, via Claude Code This site

Claude Code ran in a cloud container with repository access, so it could run the test suite and drive a real browser against its own output. That mattered more than it sounds: implementation B reported that its environment gave it no shell or browser, so it could verify its work only by reasoning about the equations. Its first delivery had correct physics and a website that did not run at all — three single-character syntax errors — and nothing in its own process could have caught that.

Tools

  • Git and GitHub for version control — 68 commits, all work on one branch, with the decision log updated alongside the code rather than reconstructed afterwards.
  • Node's built-in test runner for the 65-test physics suite. No test framework was installed.
  • Playwright for browser verification during development, installed without saving so it never became a project dependency.
  • Netlify for hosting.

The site itself has no build step and no runtime dependencies, so deployment is nothing more than pushing files. That was a deliberate constraint: it keeps what is served identical to what is written, which matters when two models have to produce comparable work and a third party has to read both.

Two things about these are worth more than their wording. First, the planning prompt asked to be questioned, and the four clarifying questions that came back changed the design before a line was written. Second, the prompts get progressively more specific about verification rather than about features — which is the direction the project kept discovering it needed to move.

4Planning and iteration

The project ran in four passes, and the structure was chosen so that mistakes would surface early and cheaply:

  1. Plan before code. A full implementation plan was written first — file structure, a frozen module API, the physics with derivations, the interaction design for every draggable element, phases with hand-checkable acceptance criteria, worked examples with expected numbers, and a ranked list of the places an implementation was most likely to go wrong.
  2. Independent critique. The plan was handed to a different model with explicit instructions to attack it and to separate errors from omissions from preferences.
  3. Adjudication. Every critique point was checked before being accepted — several by recomputing the disputed quantity from scratch. Two were accepted but implemented differently from the fix that was proposed, because the proposed fix would have introduced a different problem.
  4. Implementation against a fixed bar. The physics module and its test suite were written and made to pass before any rendering code existed. A wrong number and a wrong drawing can agree with each other, so the numbers were pinned down while they were still the only thing on screen.

The decision log marks every point where a model's recommendation was overridden. These are the ones where the two of us actually disagreed:

5The physics

The model is deliberately the simplest one that is still honest for this duty: dilute solute, isothermal and isobaric operation, constant molar flows L and V, a straight equilibrium line y* = m·x through the origin, and counter-current contacting. Those assumptions are what make every result below closed-form, and therefore checkable by hand.

The operating line, and why L is not an input

An overall solute balance around the whole column gives

V(yin−yout)=L(xout−xin)

so the operating line is straight, runs between the two column terminals (xin, yout) at the top and (xout, yin) at the bottom, and has slope

LV=yin−youtxout−xin

This is why the tool has you drag two endpoints rather than type in a liquid rate. With the feed conditions fixed, those two endpoints carry exactly two degrees of freedom, and the mass balance then determines L/V. The liquid rate is not something you set independently; it is what your choice of outlet compositions implies. Dragging the upper-right endpoint, xout, to the right is the act of choosing a smaller liquid rate.

The absorption factor

A=LmV=L/Vm

A single dimensionless group does most of the work here. It compares the liquid's capacity to carry solute against the gas's tendency to hold on to it. A > 1 means the solvent has more than enough capacity and the column is limited by the purity you demand; A < 1 means it does not, and the column is limited by the solvent. A = 1 is the balanced case, and it is a genuine removable singularity in every formula below — the expressions all go to 0/0 there and have to be handled by their limits.

One thing worth stating plainly, because it is easy to assume otherwise: A < 1 is not infeasible. A column with A < 1 still works and still has a finite height; it is simply operating nearer its solvent-limited pinch. In this tool, A falls below 1 on every preset as you drag toward the minimum liquid rate.

The tray column: Kremser

Stepping off equilibrium stages on the y–x diagram produces a staircase, and for straight lines that staircase has a closed form — the Kremser equation:

N=ln[(1−1A)R+1A]lnAwhereR=yin−mxinyout−mxinN=R−1whenA=1

N is the number of theoretical stages, and it is generally fractional. Real trays do not reach equilibrium, so an overall efficiency converts it to hardware:

Nact=⌈NEo⌉Ztray=NactS+htop+hbot

The ceil is the whole reason a tray column's height is quantised: you cannot install 3.5 trays. Drag the specification slowly and you will see the tray count sit still and then jump.

The packed column: transfer units

A packed column has no stages. Mass transfer happens continuously up the bed, so instead of counting stages you integrate the driving force:

NOG=∫youtyindyy−y*Z=HOGNOG

NOG is the number of overall gas-phase transfer units — a measure of how hard the separation is. HOG is the height of a transfer unit — a measure of how good the hardware is. The separation duty and the hardware quality are cleanly separated, which is why changing the packing in the demo moves the height but leaves NOG untouched.

For straight lines the integral has a closed form, the Colburn equation:

NOG=ln[(1−1A)R+1A]1−1ANOG=R−1whenA=1

Notice that the numerator is identical to Kremser's. That is not a coincidence; it is the structural reason the two column types are so tightly linked.

There is also a third, equivalent route that is worth knowing because it is the one most often used by hand: for straight lines, NOG = (yin − yout) / Δlm, where Δlm is the log-mean of the driving forces at the two ends of the column.

The link between them: HETP

Dividing Colburn by Kremser, the shared numerator cancels and leaves a pure function of A:

NOGN=AlnAA−1≡g(A),g(1)=1HETP=ZN=HOGg(A)

HETP — the height equivalent to a theoretical plate — is the translation between the two languages: the depth of packing that does the job of one equilibrium stage. When A = 1, HETP is exactly HOG; away from 1 they differ by g(A).

It is worth being clear about what this identity does and does not prove. The demo shows the check N × HETP = Z, and it always passes — but it passes by construction, because HETP is defined as HOG·NOG/N. It is a useful consistency check (it would catch an inverted g(A)), but it is not independent evidence that the physics is right. The checks that are independent are described in section 8.

The pinch

The operating line must stay above the equilibrium line everywhere between the two terminals, or the driving force changes sign and the solute transfers the wrong way. Because both lines are straight, their difference is linear in x, so its minimum is at one end or the other. The whole constraint therefore reduces to two conditions, one per end:

yout>mxintop pinch: a purity limityin>mxoutbottom pinch: the minimum liquid rate

Each is governed by exactly one of the two drag handles, which is why the tool can enforce them with two independent limits rather than a constraint solver. The top condition is a thermodynamic limit: no column of any height, with any liquid rate, can produce gas leaner than equilibrium with the entering liquid. The bottom condition gives the classical minimum liquid rate,

(L/V)min=yin−youtyinm−xin

at which the required height goes to infinity. Real designs run at some multiple of it — the demo reports that multiple, because it is the number a designer actually cares about.

6Staged versus continuous contacting

This is the conceptual heart of the comparison, and the composition-against-height plot is where it becomes visible.

In a tray column, contact happens at discrete locations. Gas bubbles through the liquid on a tray, approaches equilibrium with it, then travels unchanged to the next tray. The composition profile is a staircase: flat between trays, jumping at each one. The natural unit of design is the stage, and the natural question is "how many?"

In a packed column, contact happens everywhere. Liquid films flow over the packing surface while gas moves past them continuously, so the composition changes smoothly with height. The profile is a curve. The natural unit is the transfer unit, and the natural question is "how tall?"

These are two descriptions of the same physics, not two different physics. That is exactly what HETP expresses: the packing depth equivalent to one stage. A packed column can be described in stages and a tray column can be described in transfer units; each is just more natural in its own setting. The tool makes the equivalence concrete by computing both for the same duty and showing that they agree.

One asymmetry survives the translation, and it is physical rather than notational: the tray column's height is quantised and the packed column's is not. A tray column can only be built in whole trays, so its height moves in steps of one tray spacing divided by the efficiency; a packed bed can be built to any depth. In the demo, the packed height moves continuously as you drag while the tray height sits still and then jumps.

7Choosing trays or packing

The sizing calculation does not, on its own, decide the hardware. In practice the choice is driven by service characteristics. The usual reasoning:

Packing tends to win when

  • The service is corrosive. Ceramic and plastic packings tolerate duties that would demand expensive alloy trays.
  • Pressure drop matters. Packing has a much lower pressure drop per theoretical stage, which is decisive under vacuum and valuable whenever compression costs money.
  • The system foams. Packing provides less of the violent gas–liquid agitation that generates and stabilises foam.
  • The column is small. Below roughly 0.6 m in diameter, installing and maintaining trays is awkward and packing is usually cheaper.
  • Liquid holdup should be low — for heat-sensitive material, or where inventory is a safety concern.

Trays tend to win when

  • Solids or fouling are present. Trays are far easier to clean, and packing plugs.
  • The column is large in diameter. Liquid distribution across a wide packed bed is genuinely difficult, and poor distribution quietly destroys efficiency.
  • Side draws, feeds, or heat exchange are needed at intermediate points. Trays give natural, well-defined locations for them.
  • Turndown matters. Trays generally hold their efficiency over a wider range of throughput.
  • The liquid rate is very high, or the design must be scaled from data with high confidence — tray behaviour is more predictable.

A reasonable summary: packing buys low pressure drop and corrosion tolerance; trays buy robustness, predictability, and access.

8How the numbers were verified

Every formula above was checked numerically before it was written down, and the implementation is covered by a test suite that runs on Node's built-in test runner with no dependencies. Three checks carry most of the weight:

  • The stepped staircase against Kremser. Two entirely different algorithms — an iterative geometric construction and a closed-form equation — must agree to within 10−12. This is the check that catches a subtly wrong stage count.
  • Numerical integration against Colburn. The transfer-unit integral is evaluated by Simpson's rule and compared against the closed form.
  • The log-mean driving force against Colburn. An independent algebraic route that never touches A at all.

The most instructive failure found during development was in stage counting. The obvious way to handle a fractional last stage — step whole risers, then interpolate the last one linearly — is wrong, and wrong by an amount that looks like rounding: on the default preset it gives 2.375 stages where the correct answer is 2.459. The correct rule comes from the fact that the stepping recursion is geometric rather than arithmetic, so the fractional stage must be interpolated logarithmically. The test suite asserts the wrong answer explicitly, as a guard against the correct rule being quietly replaced.

What the default numbers are. The equilibrium slopes, HOG values, tray efficiency and spacing are illustrative typical figures — chosen so the demonstration is legible and every result is checkable by hand, not transcribed from a particular source. Each carries a typical range and a one-line basis in the code, collected in the sourcing table in the project's decision log.

Two of them are worth knowing about specifically. The tray efficiency, Eo = 0.70, sits at the optimistic end of the band usually quoted for absorbers; it is kept because the worked examples are built on it, not because it is a safe assumption. And the equilibrium slopes are the softest numbers here — a Henry's-law slope depends on system, temperature and pressure, so a single figure is an order-of-magnitude illustration. The SO₂ preset carries an extra warning of its own, because real SO₂–water equilibrium is distinctly curved even at low concentrations; that preset is in the list precisely to show where the straight-line assumption gives out.

9What I learned, and what's next

Four things happened in this project that are worth reflecting on, because each one was a surprise at the time:

  1. Two different models produced bit-identical physics. Across 4,837 operating points the two implementations returned the same doubles — not close, identical. Where the specification was prescriptive, all variation vanished; where it was silent, the two diverged completely.
  2. The plan contained a physics error that the critique caught. The fractional-stage rule gave 2.375 where the correct answer is 2.459432 — wrong by an amount that looks like rounding. Both implementations then got it right, because by then the plan explained it.
  3. The test suite was wrong, and the second implementation found it. It had quietly come to depend on things only the first implementation had, so it was really asking "is this the same code?" rather than "is this correct?".
  4. Passing every test is not the same as working. Implementation B once scored 60/61 on physics while its website was completely dead.

What I learned — your version. The four above are what the record shows; what you took from them is yours. Questions worth answering:

  • What surprised you about the separations once you could drag it? The quantised tray height versus the continuous packed height is the obvious candidate — did seeing it move change how you think about HETP?
  • Did the critique step change how much you trust a single model's output? Note that the critic was itself confidently wrong twice, with correct conclusions supported by faulty reasoning.
  • Three separate times in this project, an automated check disagreed with a piece of work and the check turned out to be wrong. Does that change how you would set up verification next time?

What I want to learn next. The unbuilt features below are the natural starting point — which of them actually interests you, and why? Column diameter from flooding is the one that would most change the tool, since it would make "same duty, different sizing" true in two dimensions rather than one. Curved equilibrium is the one that would most change the physics, because it retires the closed-form solutions entirely and forces everything numerical.

Features designed for but deliberately not built

The architecture was built with these in mind, so each could be added without restructuring what exists:

  • Column diameter from flooding. Trays and packing have different capacity limits, so "same flow rates, different sizing" would extend to diameter as well as height.
  • The operating envelope. Dragging the gas rate up to show weeping, entrainment and flooding on trays against loading and flooding in packing.
  • A trays-or-packing scenario sorter — a drag-and-drop exercise built from section 7.
  • Curved equilibrium lines. The honest version of the SO₂ case. All equilibrium evaluation in the code already goes through a single function, deliberately left uninlined, so that a curve can replace the straight line without touching the rest.
  • Pressure drop comparison, and the operating-cost argument that follows from it.
